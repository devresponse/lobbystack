### Do these on GitHub

The first three finish what fork PRs #169 and #187 started, so that `releases/r2` and `develop/r2`, which deployments build from, are checked like `main` (AUDIT-001 in [the technical audit](../reviews/technical-audit-2026-11-14.md)). On 2026-11-23 no branch was protected, the repository had no ruleset, and Dependabot had never opened a pull request.

1. **Protect `releases/r2`.** In **Settings** > **Rules** > **Rulesets**, choose **New ruleset** > **New branch ruleset**, set **Enforcement status** to **Active**, and add `releases/r2` as a target by pattern. Require the status checks `validate`, `Analyze JavaScript and TypeScript` and `CodeQL`, and turn on **Require branches to be up to date before merging**. With an empty bypass list the ruleset holds for everyone, the owner included: every change then reaches `releases/r2` through a pull request whose checks passed on top of the branch's latest commit, and a commit pushed straight to it is refused.
2. **Protect `develop/r2` the same way, or more lightly.** Several pull requests a day merge there, and **Require branches to be up to date before merging** makes each of them wait for a new run after every other merge. Without that setting a pull request can merge on checks that ran before another one landed, and the full run that each push to `develop/r2` starts is what shows a break between the two. Read that run before `develop/r2` moves into `releases/r2`.
3. **Turn on Dependabot, and choose the branch it updates.** GitHub keeps version updates off on a fork until the owner chooses **Enable** beside **Dependabot version updates** in **Settings** > **Advanced Security**. Dependabot reads `.github/dependabot.yml` from the default branch, and since fork PR #173 `main`'s copy has the `releases/r2` entries, so its pull requests would go into `releases/r2` directly, past `develop/r2`. To send them through `develop/r2`, change the three `target-branch: releases/r2` lines to `develop/r2` in the file on `main` and `alloplace/r1` ([guide 7.22](../deployment/guide/part-7-operations.md#722-upgrade-pinned-versions)).
4. **Delete the branches whose work has landed,** on the repository's **Branches** page: `feature/receptionists`, the old name of `releases/r2`, whose fork PR #129 was closed unmerged on 2026-11-23 because all of it is in `releases/r2`; `claude/project-thread-esl433`, from fork PR #125, closed unmerged, whose two guards reached `devops/bootstrap.mjs` another way; and nine branches whose tips are in `develop/r2`, `claude/project-thread-` followed by `1pghyq`, `3ovm3i`, `c2amif`, `f8xzld`, `h2zn1c`, `hu3odo`, `my5guu`, `q0t8ow` and `sjmug7`.

2. **Coverage that measures everything,** before the floors of 2026-12-16: a PostgreSQL service on CI's `coverage` job, as the database job has, and the agent core, the providers, `shared`, `jobs` and the control panel added to `pnpm test:coverage`, which today runs only the admin's, the worker's, `db`'s and `domain`'s tests ([development](../development/README.md#see-how-much-the-tests-cover)).
3. **Tell every waiting tab when a live updates subscription fails.** In `apps/admin/src/lib/realtime-subscriber.ts` (fork PR #196), a Redis `SUBSCRIBE` for a business that fails without the connection closing drops the tabs that joined meanwhile without telling them, and their streams keep pinging, so the browser never reconnects. A tab that joins while the subscribe is under way also hears "ready" before Redis has confirmed it, so an event in that gap is lost.
4. **Make document failures that can't change final.** A text longer than the cap, an unsupported type or a parser error comes back as a plain error, so the job runs the extraction again, up to 5 times, each possibly minutes of OCR on the worker that also holds calls. Fork PR #190 made only the memory and time limits final (`apps/worker/src/documentExtraction.ts`, `apps/worker/src/handlers.ts`).
5. **Write the way from `main` to the r2 release** in part 7 of the guide. A database at `0132`, as on both demos, would get two contract migrations together with their expand halves, `0137` with `0143` and `0146` with `0147`, which migrate refuses in one run since fork PR #199. The way: stop the admin and the worker, run migrate once with `LOBBYSTACK_ALLOW_CONTRACT_WITH_EXPAND=true`, then start the new release ([7.3](../deployment/guide/part-7-operations.md#73-database-migrations)).
6. **Let plan checkout read the deployment's own provider.** `polarCheckoutConfigured` reads only `POLAR_ACCESS_TOKEN` and `POLAR_ORGANIZATION_ID`, so a Stripe deployment without them offers no plan checkout, portal or **Cancel plan** on its plan screens and sells no plan through the API, though it sells packs, and a pack business there can't move to a subscription. Since fork PR #224 every sign-up there meets plans whose buttons are off. Use the provider's own check in the billing, promo and public API routes and the plan list, then try checkout, the portal and **Cancel plan** on a Stripe sandbox ([billing](../billing/README.md#know-the-known-problems)).
7. **Limit the bookings a website chat can make.** The receptionist's `bookAppointment` (`packages/agent-core/src/tools.ts`) books under any phone number typed in a chat, with no cap per chat, per number or per day. Turnstile's check (fork PR #174) is asked once per widget session, so a person, or a script slow enough, can still fill a day's openings. Too tight a cap refuses real bookings, so the limits are the maintainer's to pick ([website widget](../features/website-widget.md#stop-scripts-from-spending-a-businesss-chats)).
8. **Run the previous release against the new schema in CI,** the half of AUDIT-024 that fork PR #199 left: a job that migrates a database with the new migrations and runs the release before it against that database. It would flag item 5's case when it merges. `scripts/e2e-local.sh` already brings up a stack of its own, so the main cost is a second checkout ([the second check](../reviews/technical-audit-2026-11-14.md#know-what-the-second-check-found)).
9. **Small ratchet steps,** each making a backlog number smaller: the three smallest lint rule families switched off, 16 hits between them; the two help panel journeys on `/en/login` in `apps/admin/e2e/help-pages.e2e.ts`, which each needed a retry in a release gate run, most likely by clicking before the page hydrates; and ESLint for the worker and the packages, which lint with `tsc` alone, so the two promise rules that found five mistakes in the admin (fork PR #204) don't run on the code that holds calls.
