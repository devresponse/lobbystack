# Run two or more copies, 2026-11-13

On 2026-11-13 the code on `releases/r2` at `c2f99a7` was read for what happens when the admin and the worker each run as two or more copies on Railway, and for what scaling on demand would do to the system's stability. The full report, *LobbyStack scalability review: two or more admins and workers*, is a 13-page PDF in the project's files. This page keeps its findings and what happened to each since. Numbers are computed from the code unless marked measured; nothing was measured on Railway.

## Know the answer

Most of the system was already safe with copies. Three things weren't, and each would have hurt as soon as a second copy started: the database's connections, the admin's lack of time to finish at a release, and how the admin reached the worker. Fork PR #168 fixes all three. The report recommends a fixed two admins and two workers after those fixes and a rehearsal on a test environment, no autoscaling of the worker, and PgBouncer from three copies of each.

## Know what was already safe

- **Background jobs:** BullMQ runs each scheduled job once whatever the number of workers, and the jobs queued at start have fixed IDs, so a second worker adds none.
- **The outbox:** each dispatcher claims rows with `SKIP LOCKED` and a lease, so two never send the same one.
- **Calls:** one worker answers each session, through a lock in Redis, and every worker looks for calls whose worker died once a minute ([voice runtime](../voice/runtime.md)). Any worker can end a browser session or record a greeting.
- **Everything else shared:** limits and sign-in sessions live in Redis, files in the bucket, migrations take a lock, and nothing runs from cron.

## Know the three fixes

| # | Found | Fix, in fork PR #168 | Tested by |
| --- | --- | --- | --- |
| 1 | **The database would run out of connections.** Postgres accepts 100, 97 once its administrator's 3 are kept aside. At the code's defaults one admin copy can open 52 connections (40 outside a finance export) and one worker 16. Two of each could ask for 112 to 136, and 144 or more while a release's old copies finish beside the new ones; past the limit, sign-ins, chats and call steps fail. | A new database is made with room for 200 (`POSTGRES_INITDB_ARGS=-c max_connections=200`), and each copy gets a smaller share: on the admin `LOBBYSTACK_APP_POOL_MAX=8`, `AUTH` 4, `WORKER` 8, `DISPATCHER` 2 and `FINANCE_EXPORT` 2, 24 in all; on the worker `WORKER` 10 and `DISPATCHER` 2, 12 in all. Two admins and two workers then need at most 144 in a release's first minute, and three admins with two workers 192, within 197. An existing database is raised with `alter system set max_connections = 200;` and a restart ([guide 7.24](../deployment/guide/part-7-operations.md#724-scale-up)). The report's 22 per admin left out the finance export's 2; the code's budget counts every pool. | `packages/db/src/pool-budget.test.ts`, `scripts/bootstrap.test.ts` |
| 2 | **The admin was stopped at once at every release.** Railway's draining time defaults to 0 seconds, so requests in flight failed, including a new call's attach, which the admin sends after answering OpenAI. | `RAILWAY_DEPLOYMENT_DRAINING_SECONDS=60` on the admin. Next.js then finishes its requests and their after-response work before it exits. It comes with fix 1, because the old admin's connections overlap the new one's for that minute. | `scripts/bootstrap.test.ts` |
| 3 | **Every new call went to one worker.** Railway's private name for the worker lists one address per copy, but `fetch` connected to the first and kept the connection, so the other copies never got a call. When that copy was shutting down, its refusals sent each retry back to it. Measured locally on Node 26: 300 of 300 requests reached one copy, and 3 of 3 calls were turned away. | The admin looks the name up for each request, tries the copies in a random order, and passes a refused or unreachable request to the next copy at once. Only when every copy refuses an attach does it wait 250 ms, then 750 ms, looking the name up again before each round, within the same 10 seconds ([voice runtime](../voice/runtime.md)). | `apps/admin/src/lib/live-prototype.test.ts`, and `live-prototype.copies.test.ts` with two stand-in workers over real connections |

## Know the recommendations

| Recommendation | Since |
| --- | --- |
| Rehearse two admins and two workers on a test environment such as dev1 before production: test calls by phone and website, a release during a call, a stopped worker, a burst of chats. It also shows whether a worker that's shutting down leaves Railway's address list. | Not done |
| Keep the number of copies fixed. Railway sets replicas by hand and has no built-in horizontal autoscaling (checked 2026-11-13), and a worker can't hand its calls to another, so taking one away waits up to 31 minutes for its calls. Autoscale the worker only after a call hand-over at release exists. Never let a production service sleep. | Advice |
| Soon after the fixes: a cap on calls per worker answered with the same 503, rate limits in the jobs that call Polar, Resend and the shared text number, a ready check that waits for the schema, signals and a watchdog per copy, Postgres memory settings, and a check of the call connection's compression. | Not started |
| Later: a Postgres standby with point-in-time recovery (Railway's own image), a Redis standby, one job per type instead of a schedule per business, PgBouncer from three copies of each, a call hand-over at release, one Redis subscriber per admin, an autoscaler, and cells ([roadmap](../roadmap/scale-past-one-stack.md)). | Not started |

Not checked: the order in which Railway's private name lists the copies, whether a copy that's shutting down leaves it, and whether OpenAI compresses the call's control connection.
