# Review the website widget, 2026-10-15

On 2026-10-15 the website widget was reviewed at `508f659`: its code, a production build run in a browser, and every request and SQL statement it made. It found the widget sound, with six bugs visitors could hit, settings to change and a heavy first download. Fork PR #22 fixed the six bugs the same day, and fork PRs #23 to #26 carried out the first four code improvements. This page keeps the findings and what happened to each. [Website widget](../features/website-widget.md) describes the widget as it works now. Timings come from a local build, so read them as relative.

## Know what held up

- **Access is scoped per website.** Each key lists its allowed websites, matched exactly, and the one-hour session token is signed, bound to the website and the visitor, and checked on every request (`apps/admin/src/lib/widget-access.ts`).
- **Every endpoint is rate limited,** in one Redis round trip, and in production refuses requests rather than run unlimited when Redis is down.
- **The loader stays dormant:** about 7 KB, one request per page view, nothing more until a visitor opens the panel.
- **Messages render safely:** HTML is escaped before the few Markdown rules run, and only `http(s)` addresses become links.
- **Visitors can't reach appointments:** the lookup, cancel and reschedule tools need a caller's number from a phone call.
- **The page and the panel check each other's origin** before acting on a message.

## Know the bugs and their fixes

| # | Bug | Fixed in #22 by |
| --- | --- | --- |
| 1 | A site's fixed elements, such as a cookie bar, covered the open panel | Giving the loader's root the panel's z-index |
| 2 | A chat the team took over never went back to the receptionist, and website chats never closed | The receptionist takes a chat back on the visitor's next message once the team has been quiet 10 minutes (`TEAM_CHAT_QUIET_MS`), and a chat idle for a day closes, so the next message starts a new one (`WIDGET_CHAT_IDLE_CLOSE_MS`) |
| 3 | A reply was lost when the visitor changed page mid-answer | Finishing and saving the reply on the server |
| 4 | The snippet in the page head without `defer` showed nothing | Waiting for the page to finish parsing |
| 5 | An unlisted website got a vague error | CORS headers on the session route's refusals, so the loader shows "This website is not authorized to load this widget." |
| 6 | The panel painted in the browser's language, then switched to the business's | The loader passing the language in the panel's address |

#22 also took PostHog out of the widget, which keeps it on the dashboard only: a first open went from 582 KB to 476 KB, with no PostHog request or storage on customers' sites.

## Know what the measurements showed

| Moment | Requests | Database writes, before the improvements | Time on a local build |
| --- | --- | --- | --- |
| Page view, bubble only | 1, the loader (6.9 KB) | 0 | 13 ms on the server |
| First open | 25, 582 KB | 8 | 1.8 s to a usable chat box |
| One chat message | 2 | 12 | 0.5 s with an instant stand-in AI |
| Reopen on the next page | 5, scripts from cache | 8 | 0.48 s to the history |

The chat box waited on four steps in a row (the page, its scripts, the business settings, then the history), and the eight writes on opening were a visitor row, the key's last use, the month's billing row three times, a second visitor update and an empty conversation.

## Set the recommended settings

On the admin service, none of them changed by the review itself:

- `AI_CHAT_REASONING_EFFORT=low`: website chat was the only AI work on the `high` default. Try a few booking chats and use `medium` if answers suffer.
- `TRUSTED_CLIENT_IP_HEADER`: without it the per-IP limits are off, so one person rotating visitor IDs can use a whole key's budget. See [widget scalability](widget-scalability-2026-10-15.md) for which header.
- `RAILWAY_DEPLOYMENT_DRAINING_SECONDS=120` on the admin, so a redeploy doesn't cut replies being written. The worker needs 1860 for calls.
- List both `example.com` and `www.example.com` in a key's allowed websites when a site answers on both.
- Treat Redis as part of the widget: while it is unreachable, every widget request answers 503.

The review's advice to keep `WEB_CALL_MAX_DURATION_MS` at a 5-minute default is out of date: since fork PR #54 website calls default to 30 minutes ([calls](../features/calls.md#end-calls-politely-at-the-time-limit)).
